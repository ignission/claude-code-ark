# 音声モード (iPhone向け)

- 日付: 2026-09-19
- 検討の経緯: 「ChatGPTの音声会話のようにしたい」という要望に対し、Fableに独立した設計意見を求め、
  その後ユーザーが利用場面・端末・方式を選んだ
- 検証の方針: 仕様の精読ではなく、検証用のArkをHTTPSで立ててiPhoneで触って判断する

## 1. 目的

スマホを手元に置いたまま (家事中など)、画面を操作せずにClaudeと往復できるようにする。
話して指示を送り、Claudeがターンを終えたら返答を耳で聞く。

## 2. 決定事項

| 項目 | 決定 |
|---|---|
| 対象端末 | iPhoneのSafari (ブラウザのタブ)。PC・Android・デスクトップアプリは対象外 (ユーザー決定) |
| 利用の前提 | 画面を点けたまま、Arkを前面に出して手元に置く。画面ロック中・バックグラウンドでは動かない (ユーザー決定) |
| 方式 | アプリ内の音声モード (ユーザー決定)。Siriショートカット + Web Pushの経路は採らない |
| 音声認識 | ブラウザ内蔵の `SpeechRecognition` (`webkitSpeechRecognition`)、`ja-JP` |
| 読み上げ | ブラウザ内蔵の `speechSynthesis`、`ja-JP` |
| 送信 | 認識した文を約2秒表示し、取り消されなければ自動で送る |
| 読み上げる内容 | JSONLで `stop_reason: "end_turn"` が付いた返答の本文。コード・表・URLは読まない |
| 質問・権限確認 | 読み上げるが、回答は画面で行う。声では答えられない |
| 割り込み | 読み上げ中の画面タップで止める。声での割り込みは作らない |
| 外部サービス | 追加しない (要約用LLM、音声API、サーバー側の音声処理のいずれも無し) |

## 3. 検討して採らなかったもの

### Siriショートカット + Web Push (画面ロックのまま使う経路)

iPhoneでは画面をロックした時点でSafariのJSが止まり、マイク・認識・読み上げ・Socket.IOがすべて止まる。
ロック中に使えるのはOSを通す経路 (Siriショートカットで入力、Web Pushの通知で出力) だけだった。
ユーザーは画面を点けたまま使うアプリ内の方式を選んだ。

### ChatGPT型の常時会話 (発話区間の自動検出、声での割り込み)

Claude Codeの1ターンは数分のツール実行を含み、「話すと数秒で返ってくる」往復にならない。
常時マイクを開いて発話区間を切り出し、スピーカーの音の回り込みを消し、声での割り込みを扱う装置は、
中身 (最後の返答を読む、声で入力する) より桁違いに大きい。Arkが4回撤去したコンテキスト機構と同じ形になる。

代わりに「読み上げが終わったら自動でマイクを開く」だけを試し、iOSに拒否されたらタップで話す形に落とす
(7章)。ハンズフリーで往復できるかは、この実装で実機に判定させる。

### Claudeに音声向けの書き方をさせる

SessionStart hookで「返答の冒頭に口頭用の要約を書け」と注入する案は、
`.claude/rules/context-engineering.md` の5章で「こだま」と判定された型そのものなので採らない。
音声モードを使っていないセッションの文体まで変わる問題もある。読み上げる側で選ぶ (5章)。

### 要約用LLM・サーバー側の音声処理

プラン枠課金を守る製品に、従量課金のAPIを混ぜる理由が今は無い。
whisper.cppやVOICEVOXをこのマシン (aarch64、4コア、GPU無し) に常駐させると、Claudeセッション群のCPUを食う。
ブラウザ内蔵の認識が実機で使い物にならなかった場合に、初めて検討する。

### 複数タブでの読み上げの重複防止

音声モードはタブごとに明示的に入るので、音声モードに入っていないタブは喋らない。
通知用のリーダー選出 (`SessionNotificationLeader`) は流用しない。

## 4. 体験の流れ

### 入り方

会話モードの下部バー (1タップ操作の列) に「音声」ボタンを出す。`SpeechRecognition` と `speechSynthesis`
の両方があるブラウザでだけ出す。押すと全画面の音声モードに入る。

この最初のタップの処理の中で、次の3つを同期的に行う (iOSはユーザー操作の中でしか許さないため)。

1. 短い読み上げ (「音声モード」) で `speechSynthesis` を使える状態にする
2. `navigator.wakeLock.request("screen")` で画面の消灯を止める
3. 認識を開始する

### 状態

| 状態 | 画面 | 抜け方 |
|---|---|---|
| 待機 | 大きなマイクボタン「タップして話す」 | タップで「聞き取り中」 |
| 聞き取り中 | 認識途中の文を大きく表示 | 認識が確定したら「送信待ち」。何も聞き取れなければ「待機」 |
| 送信待ち | 確定した文と、2秒のカウントダウン。「取り消す」「すぐ送る」 | 2秒経つか「すぐ送る」で送信して「作業中」。「取り消す」で「待機」 |
| 作業中 | Claudeの状態 (考えています / 作業しています)。「追加で話す」ボタン | ターンの終わりで「読み上げ中」 |
| 読み上げ中 | 読み上げている文。「タップで止める」 | 読み終えたら自動で「聞き取り中」を試す。拒否されたら「待機」。タップで「待機」 |
| 画面で操作 | 全画面を畳み、画面下の小さな帯に縮める | 帯のタップで全画面へ戻り「待機」 |

- 「作業中」でも話せる。Claude Codeは作業中に届いた入力を次の入力として溜めるので、そのまま送る
- 「聞き取り中」「送信待ち」のあいだに届いたターンの終わりは溜めておき、抜けた後に読む。
  「読み上げ中」に届いたものは、今の読み上げの後ろに続ける
- 送信は既存の `onSendMessage` (`session:send`) を使う。会話ビューには通常どおり送信中の吹き出しが出る
- 画面右上の「終了」で音声モードを抜ける。認識と読み上げを止め、Wake Lockを解放する

### 画面での操作が要るとき

- **質問 (AskUserQuestion)**: 質問文と選択肢を読み上げ、「画面で答えてください」と言って「画面で操作」に移る。
  全画面を畳むと、下の会話ビューの質問カードがそのまま見える
- **権限確認など (`bridgeStatus` が `AWAITING` で質問カードが無いとき)**: 「画面で確認が必要です」とだけ言って
  「画面で操作」に移る。画面のテキストは読まない (内容のパースは禁止)

声で答えられるようにしないのは、誤認識で選択肢や権限を確定させる事故を防ぐため。ttydの再接続で
Enterの合成入力を禁じたのと同じ理由である。

### 画面が隠れたとき

`visibilitychange` で `hidden` になったら、認識と読み上げを止めて「待機」にする。
戻ったときは自動で再開せず、タップを待つ (iOSはユーザー操作なしの再開を許さないことがある)。
Wake Lockは `visible` に戻ったときに取り直す。

## 5. 何を読み上げるか

### 読み上げの対象

音声モードに入った後にJSONLへ届いた、次の条件をすべて満たすレコードの本文。

「入った後」の基準は端末の時計ではなく、入った時点で届いているイベントの最大のtimestamp
(JSONLはサーバーの時計で書かれる) とする。これより新しく、まだ読んでいないidだけを読む。
iPhoneとサーバーの時計のずれに左右されず、過去履歴の追加読み込みや再接続時のsnapshotで
古い返答を読むこともない。入った時点でイベントが1件も無ければ、最初に届いたsnapshotの最大値を基準にする。

- `type: "assistant"`
- `message.stop_reason: "end_turn"`
- 本文ブロックの `type` が `"text"`
- `isSidechain` がtrueでない (subagentの発言は読まない)

`stop_reason: "tool_use"` の本文 (ツール実行の合間の短い独り言) は読まない。
自分の送信に対する返答に限らず、音声モード中に届いたターンの終わり (バックグラウンドのタスク完了で
始まったターンなど) も読む。

実データで確かめたこと (直近40ファイル): 最終返答は本文ブロックごとに1レコードへ分かれ、それぞれに
`end_turn` が付く。`end_turn` が1件も無いファイルは、`/clear` や `/mcp` などスラッシュコマンドだけで
終わったセッションだった。

終わりの判定をtmuxの状態 (`bridgeStatus` の遷移) ではなくJSONLで行うのは、状態と本文が別々の
ポーリングで届き、状態が先に変わると読むべき本文がまだ無いため。JSONLなら合図と本文が同じ1行で届く。

### 読み上げ用の文への変換

`lib/speech-text.ts` の純関数で、Markdownを読み上げる文の配列に変える。

| 元 | 読み上げ |
|---|---|
| コードブロック (```` ``` ````) | 「コードは画面で」。連続するときは1回だけ |
| 表 (`|` で始まる行の並び) | 「表は画面で」 |
| URL | 読まない。Markdownのリンク `[文](URL)` は「文」だけ読む |
| インラインコード | 24文字以下なら中身を読む。それより長ければ読まない |
| ファイルパス (`/` を2つ以上含む語) | 最後の要素 (ファイル名) だけ読む。行番号の `:12` は落とす |
| 見出し・強調・箇条書きの記号 | 記号を落とす。箇条書きの各項目は1文として扱う |
| 絵文字 | 落とす |

句点・改行で文に分け、先頭から合計300文字に収まるところまでを読む。残りがあれば最後に
「続きは画面で」を足す。文ごとに `SpeechSynthesisUtterance` を分けて順に読む (長い1発話が途中で
切れる不具合を避けるため)。

## 6. 構成

### 新しく作るもの

| ファイル | 役割 |
|---|---|
| `packages/web/src/lib/speech-text.ts` | Markdown → 読み上げる文の配列 (5章)。純関数 |
| `packages/web/src/lib/voice-turn-signals.ts` | JSONLイベント列から、音声モード開始後の新しいターンの終わりを取り出す。読み済みのidを受け取り、重複して読まない。純関数 |
| `packages/web/src/lib/voice-mode-machine.ts` | 4章の状態遷移。状態と入力 (タップ、認識結果、ターンの終わり、質問、読み上げ終了、エラー、画面の表示状態) から、次の状態と副作用の指示を返すreducer。純関数 |
| `packages/web/src/lib/browser-speech.ts` | `SpeechPort` インターフェース (認識の開始・停止、読み上げ・中止、Wake Lock) と、ブラウザAPIによる実装 |
| `packages/web/src/hooks/useVoiceMode.ts` | reducerと `SpeechPort` をつなぎ、副作用を実行する。診断ログをサーバーへ送る |
| `packages/web/src/components/VoiceModeOverlay.tsx` | 全画面の音声モードと、畳んだときの帯 |

`SpeechPort` を挟むのは、状態遷移とフックのテストをブラウザの音声APIなしで回すため。

### 既存への変更

- **`jsonl-event-parser.ts`**: `RawJsonlMessage` に `stop_reason` を足し、`assistant-text` イベントに
  `endTurn?: boolean` を載せる
- **`SplitChatPane.tsx`**: 親へ渡すコールバックを2つ足す。`onEventsChange(events)` と、
  既存の `onActiveAuqChange` と同じ作法の `onActiveAuqDetail(auq | null)`。JSONLの購読は増やさない
  (サーバーは1接続1セッションにつき購読を1つしか持たず、2つ目は無視され、解除すると会話ビュー側も切れる)。
  1,847行あるので、足すのはコールバックの呼び出しだけにする
- **`MobileSessionView.tsx`**: 音声モードの開閉を持ち、`VoiceModeOverlay` を描く。
  `onEventsChange` で受けたイベントは親のstateに置かず、音声モードが開いているときだけフックへ渡す
  (会話ビューの再描画を増やさないため)。音声モードに入るときは表示を会話モードにする
  (会話モード以外ではJSONLの購読が止まるため)
- **`mobile-quick-actions.ts`**: `"voice-mode"` を足す。会話モードで、音声APIが使えるときだけ出す
- **`packages/shared/src/types.ts` とサーバー**: クライアント → サーバーのイベント
  `voice:diagnostic` (`{ sessionId, kind, detail }`) を足す。サーバーはpm2のログへ1行出すだけで、
  保存も配信もしない。`detail` は長さを切り詰め、認識した文や返答の本文は送らない (文字数だけ)

### データの流れ

```text
話す → SpeechRecognition → 送信待ち (2秒) → onSendMessage → session:send → tmux → claude
claude → JSONL → JsonlTailManager → session:jsonl-line → useSessionJsonl (SplitChatPane)
  → onEventsChange → voice-turn-signals → speech-text → speechSynthesis
session:auq → SplitChatPane → onActiveAuqDetail → 読み上げ → 画面で操作
```

## 7. iOSの制約と対処

調べて分かったことと、実機でしか確かめられないことを分けて書く。

### 分かっていること

- 画面ロック・バックグラウンドでは認識も読み上げも止まる。前面のタブで読み上げが壊れる報告は無い
- 認識の開始はユーザー操作を要する。操作なしの `start()` は `not-allowed` になることがある
- iOSの認識は、途中結果が来ないまま数秒待たされる、確定の合図が遅いといった報告が多い
- Screen Wake LockはiOS 16.4以降のSafariで使える
- マイクと認識はHTTPSでしか動かない

### 実装での対処

- **自動でマイクを開く**: 読み上げの終了イベントの中で `start()` を試す。`not-allowed` や開始失敗なら
  「待機」に落ちてマイクボタンを出す。どちらになったかは診断ログに残す
- **確定が遅い**: `continuous: false`、`interimResults: true` で使う。途中結果が1.2秒変わらなければ
  `stop()` を呼び、最後の途中結果を確定として扱う。`onresult` の確定が先に来ればそちらを使う
- **認識のエラー**: `no-speech` と `aborted` は「待機」へ静かに戻る。`not-allowed` と
  `service-not-allowed` は、iPhoneの設定で音声入力 (Siri) とマイクの許可を確かめるよう画面に出す。
  `network` と `audio-capture` はエラー名を画面に出して「待機」へ戻る
- **読み上げの声**: `getVoices()` から `ja-JP` の声を選ぶ。無ければ `lang` だけ指定して任せる

### 実機でしか確かめられないこと

1. 認識の精度と安定性 (途中で止まらないか、確定までの時間)
2. 読み上げ後に操作なしでマイクを開けるか
3. 認識の後に、読み上げが受話口から小さく鳴らないか

3が起きたら、Safariの `navigator.audioSession.type` で読み上げ前後に切り替える対処を検討する。
初版には入れない。

## 8. 検証

### 自動テスト (vitest)

- `speech-text`: 5章の表の各行、300文字での打ち切り、コードブロックの連続
- `voice-turn-signals`: `end_turn` の本文だけを拾う、`tool_use` とsidechainを除く、開始前の履歴を読まない、
  同じidを二度読まない、`/clear` 後の空snapshotで壊れない
- `voice-mode-machine`: 4章の状態表のすべての遷移、自動でマイクを開けなかったときの落ち方、
  画面が隠れたとき、読み上げ中のタップ、作業中の追加入力
- `jsonl-event-parser`: `endTurn` が載ること
- `mobile-quick-actions`: 会話モードで音声APIがあるときだけ `"voice-mode"` が出ること
- `VoiceModeOverlay` / `useVoiceMode`: 偽の `SpeechPort` で、話す → 送信 → 読み上げ → 自動で聞き取り、の一巡

`pnpm check` と `pnpm test` を通す。

### 実機での確認 (マージ前のゲート)

本番とは別のデータディレクトリとポートで検証用のArkを立て、`--quick` でQuick TunnelのHTTPS URLを出す。
本番のdistは上書きしない。ユーザーにiPhoneのSafariで開いてもらい、検証用セッションで次を試してもらう。

1. 音声モードに入り、短い指示を話して送る
2. Claudeの返答が読み上げられ、その後に自動でマイクが開くか
3. コードを含む返答で「コードは画面で」になるか
4. 質問 (AskUserQuestion) が来たときに読み上げて畳まれるか

認識のエラー、自動でマイクを開けたか、各段階の時間は `voice:diagnostic` でサーバーのログに残るので、
ユーザーに報告してもらうのは聞き取りやすさ・声の大きさ・使い心地だけでよい。

## 9. 対象外

- 画面ロック中・バックグラウンドでの動作
- PC、Android、デスクトップアプリ (Electron)
- 声での割り込み、発話区間の自動検出、常時のマイク
- 声での質問・権限確認への回答
- 読み上げの速さ・声の選択の設定画面
- 要約用LLM、外部の音声API、サーバー側の音声処理
- PWA化、Web Push
